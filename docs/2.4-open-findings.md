## Open

### 1. Token assurance records have no retention policy — Task 5
`auth_token_assurances` stores what a person proved and when: factor ids, credential ids,
timestamps, subject. That is **more** sensitive than the Sanctum row it describes, which is
an id and a hash. `VouchPruneCommand` never touches the table, and both
`sanctum:prune-expired` and `$user->tokens()->delete()` hard-delete tokens without telling
Vouch, so records outlive their tokens indefinitely.

**Do not prune by `weakest_satisfied_at`.** That is evidence age, not token age: a
legitimately long-lived token has an old anchor, so an age-based sweep deletes records for
LIVE tokens, and under default-deny they then stop working with no diagnosable cause.

The sound mechanism is an orphan sweep driven by an issuer existence check, since only the
issuer knows whether a token still exists. Recorded: addendum §3c.

### 2. `lockSubject()` is not a durable per-subject lock — Task 5
It locks the first `auth_sessions` row for the user. Adequate for issuance, where a session
always exists; inadequate for a subject-wide sweep, which must serialize against a subject
that may have no live session at all. Raised by the implementer at Task 3 consensus.

Note `CredentialLockManager::canonicalCredentialIds()` is the single credential order and
must be used rather than `orderBy('id')`: the ids are opaque strings, so `'09'` and `'9'` are
different credentials and primary-key order cannot express that.

### 3. Machine-token issuance has no path — Task 4/6 boundary
`Vouch::issueToken()` refuses machine grants outright and the design still calls for a
separate machine path. Task 4 can ENFORCE existing machine records but must not become the
first consumer that also creates them.

### 4. Tenant-scoped issuance is unreachable — wiring gap
`SessionLifecycle` persists evidence with a null tenant, so no session can produce
tenant-scoped evidence and a tenant grant has nothing to match. Issuance refuses, which is
correct and fail-closed.

This is **not** an `aal3`-style vocabulary gap: the flow already knows the attempt's tenant
and drops it before the session writer, and the persisted proof already carries `tenant_id`.
No new column is needed. Follow-up: carry the attempt tenant into `AuthSuccess` and through
to persisted session evidence.

### 5. `aal3` is unsatisfiable with the shipped vocabulary — host-facing docs
`NistAssuranceVocabulary` caps at `aal2` by design, because AAL3 needs hardware-binding
evidence the kernel never observes. A host configuring an `aal3` requirement has built a
route nobody can reach, and it fails closed silently. The kernel's own test asserts the cap;
only fabricated rows ever carried `aal3`. Needs saying in host documentation.

### 6. `AssuranceEvidence::derivedAcr()` resolves the vocabulary through `app()`
A readonly value object depending on ambient container state: the same evidence can derive
different levels, and `toArray()`/`fromArray()` are pure while `derivedAcr()` is not. Fixing
it means moving vocabulary resolution to the adapter boundary across every caller and any
host shipping a custom `AssuranceVocabulary` — a cross-cutting change deferred by agreement
at Task 2a consensus, not an oversight.

### 7. The mutation corpus predates `src/Assurance/`
`HANDOFF.md`'s ledger was measured before 2.4 existed. Every `(file, mutator, expression)`
tuple touching assurance is stale, and 2.4 also changed four authorization call sites.
Re-measure before trusting a row in it.

### 8. Nothing guards a new table shipping without a retention policy
Finding 1 was missed because no test would have caught it. Filed as an acceptance criterion
of [#3](https://github.com/fissible/vouch/issues/3) rather than separately: a blanket "every
`auth_*` table is pruned" rule would be wrong, since some tables are deliberately retained.
The enforceable form is a checked manifest of package-owned persistent tables, each either
pruned or listed as retained with its reason.

## Closed during the phase, with the answer

### Expired vs revoked tokens cannot be distinguished — not a bug, do not file upstream
Measured against the shipped driver: an expired token and a revoked one both make
`resolveForRequest()` return null, so neither reaches the adapter. Sanctum hard-deletes on
revoke — no `revoked_at`, no soft delete — so revoked is indistinguishable from
never-existed **in the database**, not merely in the API. Retaining revoked tokens would
change Sanctum's storage model and retention surface; an upstream issue would rightly be
rejected.

Expired IS recoverable via `Sanctum::authenticateAccessTokensUsing()`, a documented hook
receiving `($accessToken, $isValid)`. Vouch does not claim it: that is global mutable state
on a third-party facade and would collide with any host already using it. Recorded: §3b.

### The per-driver CHECK constraints work on all three engines
Flagged as SQLite-only when the PR opened, since the constraints are raw per-driver DDL and
MySQL commits DDL implicitly. Verified against Docker MySQL 8 and PostgreSQL 16 locally, then
by the CI matrix. Resolved.

### The token gate shipped armed by default — fixed in Task 4
`RejectsUnrecordedTokens` installs itself into `web` and `api`, and §6.5 point 4 forbids
backfilling, so an armed default would have invalidated every Sanctum token a host had ever
issued the moment the package booted. `vouch.token_gate.mode` now defaults to `observe`,
following the rule this package already applies to throttle dimensions with a far smaller
blast radius.
